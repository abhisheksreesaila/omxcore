How omxcore got fast

The same 22 TPC-H queries, run again after every optimization: each in a fresh Python process, data already in memory, no warm-up, the clock covering only the query and its materialized result, every result checked against DuckDB. The page is also an argument that Mojo is a good language for a data engine, so each card says which Mojo feature it relies on, and says so plainly when the win is ordinary engineering that any language would get.

Which Mojo features the engine uses

AOT shared libraries over the Arrow C Data Interfacemojo build --emit shared-lib, called from Python with ctypes; Mojo reads Arrow buffers in place and Arrow wraps the result without a copy. No JIT warm-up inside a query.
Closures inlined into parallelizeEvery pass over the rows is a capturing closure run on all cores (morsel-driven, work-stealing through an atomic counter).
Compile-time specializationOne interpreter body, compiled into specialized versions (keyed, shared); the key encoder closure is inlined, with no virtual call per row.
SIMD widthsSIMD[DType.float64, W] with W = simd_width_of[...](): aggregation lanes sized for the CPU it was compiled for.

Read these numbers honestly

  • The lead over DuckDB rests on Q21. Leaving it out, DuckDB's SF10 total is lower than omxcore's (the per-query chart above shows how many queries DuckDB still wins). Q21 benefits from TPC-H's stored order.
  • Engine-only is the headline. Loading data is outside the clock. omxcore still reads Parquet through PyArrow, which the user-felt scoreboard in the benchmarks document includes.
  • Not every win is Mojo. Cards badged "plain engineering" are algorithms or fixed costs any engine could fix. The Mojo-specific part is everything that loops over rows, compiled ahead of time from code that reads like Python.
  • SF1 queries take a few milliseconds, so single SF1 figures can move by 10 to 20 percent between runs.
