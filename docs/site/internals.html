How a query runs, layer by layer

A query is built lazily in Python and handed down a stack. What happens next depends on the shape of the plan. For an aggregate over a single table (a scan with filters, then group and aggregate), each of layers 04 to 06 either runs the whole plan or declines and lets the next one try: the first to accept it runs all of it. A plan with joins is not one piece: the joins run first, in the join engine (with native filter and gather calls), and the aggregate on top of the joined table then goes down the stack. A plan that is not an aggregate (a filter, sort, limit or distinct on its own) runs in layer 06, which calls the native helpers one operator at a time. Declining is cheap and silent; the answer is the same whichever path produced it.

What you're looking atThe path one query takes through the engine, for someone who wants to port it to another stack or add an operator. The numbered stack is clickable: pick a layer and the panel beside it shows what that layer does, its files, what goes in and out, when it says "not me" and which layer answers next, and how to see which one ran. Every file, function and environment variable named on this page exists in the repo, and a test checks that.

1. The path a query takes

For a single-table aggregate, layers 04 to 06 are tried in that order on the CPU and the first to accept it runs all of it. Joins are materialised before that (see layer 06), and a plan that is not an aggregate goes straight to layer 06. Layer 07 is dashed because it sits beside the stack, not under it: device="auto" picks the device right after the optimizer, and then the stack runs on that device. The native executor is CPU only.

2. What crosses the Python ↔ Mojo boundary

One ctypes call per query into kernels_aot/libmxexec_cpu.so. Python only plans and packs; Mojo does the work. Nothing is copied on the way in, and the result is read in place on the way out.

Python · native_exec.py
  1. Check the plan shape; compile the filter and aggregate expressions to bytecode (pipeline_program.py).
  2. Export every input column chunk as an Arrow C Data Interface ArrowArray struct with Array._export_to_c. The buffers stay where they are.
  3. Pack a plan block: an int64 array of a magic number, counts, bytecode addresses and the struct addresses.
  4. Make the call: _call runs lib.mx_execute(plan_addr, out_addr).
native_exec.py · _call
Arrow C Data Interface arrays + plan block→←output block: addresses of the result buffers
Mojo · executor_cpu.mojo
  1. mx_execute checks the magic number and reads the structs in place.
  2. Filters, encodes group keys, aggregates, sorts and limits on every physical core.
  3. Writes result buffers into one arena and fills the output block.
kernels_aot/executor_cpu.mojo · mx_execute

Back in Python the buffers are wrapped without copying (pa.foreign_buffer into a pa.Table), and the arena is freed by mx_exec_free when the table is garbage collected (_Arena). Python calls each input struct's release callback after the call. If the executor returns a negative code, _decline records why and the next layer runs. Only the inputs follow the Arrow C Data Interface; the output is Arrow-layout buffers described by the output block, not exported structs. A port needs the same three things: arrays handed over as C structs, one plan buffer, one result arena.

3. Add an operator

The worked example is SELECT DISTINCT, which got its native call in F-032 (M2h, tests/test_native_distinct.py). Two later operators followed the same steps: the top-k behind a filter, try_filter_topk calling mx_filter_topk (F-046e), and try_count_distinct calling mx_count_distinct (F-046h). The rule that shapes every step: the executor never changes an answer, so the old path stays in place and the new one returns None for anything it is unsure about.

  1. Give it a plan node.

    The node is Distinct in lazy_frame.py, built by LazyFrame.distinct. A new column expression instead goes in lazy_expr.py as an Expr op. SQL reaches the node through sql_frontend.py, and validate_plan in plan_validation.py gets a rule for its invariants (for Distinct: no duplicate subset columns).

  2. Teach the optimizer about it.

    Every pass in PlanOptimizer (optimizer.py) rebuilds the tree, so each needs a branch that rebuilds the new node, as the isinstance(node, Distinct) branches do. Add a rewrite there only if the operator can be pushed or merged.

  3. Make the Python version work first.

    CustomOpsCompiler._apply_distinct_custom in custom_ops.py is the dispatcher: it tries the native call, then the group-key encoder, then _distinct_rows. Whatever the native call declines lands on the code below it.

  4. Encode it for the executor.

    try_distinct in native_exec.py exports the columns, packs the plan block (starting with DMAGIC) and calls through _call_distinct. Declare the function's argtypes and restype in _load. Return _decline("reason") for nulls, types or sizes it cannot take.

  5. Write the Mojo function.

    mx_distinct in kernels_aot/executor_cpu.mojo is an @export function with abi("C") taking (plan_a: Int, out_a: Int). It checks its magic number, returns E_BAD_PLAN for a plan it does not recognise, and writes the output block.

  6. Rebuild the library.

    Run bash scripts/build_pipeline.sh exec (scripts/build_pipeline.sh). It rewrites libmxexec_cpu.so, which is committed.

  7. Test the path, not only the answer.

    tests/test_native_distinct.py compares native, MXFRAME_NATIVE=0 and DuckDB on the same data, and asserts the native path ran (last_path), because a test that only checks the answer passes just as well when the call quietly declined. It reuses the fixtures _both, _same and native from tests/test_native_exec_m1.py.

4. Build it yourself

The Mojo sources compile ahead of time into shared libraries that ship in the wheel; nothing compiles at run time. You need pixi (the Mojo compiler comes from its environment).

# once
pixi install
pixi run setup-omxcore

# the CPU pipeline, the native executor and the GPU pipeline (scripts/build_pipeline.sh)
bash scripts/build_pipeline.sh            # all three
bash scripts/build_pipeline.sh exec       # only libmxexec_cpu.so
bash scripts/build_pipeline.sh cpu        # libmxpipeline_cpu.so + libmxexec_cpu.so
bash scripts/build_pipeline.sh gpu        # libmxpipeline_gpu.so

# the single-operator AOT kernels (step 2 of scripts/release.sh)
pixi run mojo build kernels_aot/kernels_aot.mojo -I kernels_aot \
    --emit shared-lib -o kernels_aot/libmxkernels_aot.so
pixi run mojo build kernels_aot/kernels_aot_gpu.mojo -I kernels_aot \
    --emit shared-lib -o kernels_aot/libmxkernels_aot_gpu.so

# the tests
pixi run test                             # pytest on tests/, from any checkout or worktree

The pipeline and executor libraries are built for x86-64-v3 (AVX2, FMA, BMI2) rather than the build machine's own CPU, so a wheel does not crash on an older processor. The join and group-key libraries (joinsemi_cpu.mojo, groupkeys_cpu.mojo) carry their own build command in their file header. scripts/release.sh runs the whole sequence for a release. Tests that need a library skip themselves if it is not built, so a missing .so shows up as skipped tests, not failures.
