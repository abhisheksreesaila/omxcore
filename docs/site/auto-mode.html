How device="auto" decides

With a CPU and a GPU, compute(device="auto") chooses a device for the whole query from costs it has measured on your machine. It does not stream every query's rows to both devices: on this hardware the link from host memory to the GPU is slower than the CPU cores reading the data in place. Instead it runs the first scan of a table on the CPU, copies that table's columns to the GPU in the background, and once they are there, splits an aggregate's rows between the two.

    The rules, and where they live

    1. Small inputs skip everything. Under 200,000 source rows the query goes to the CPU before the calibration is even loaded (loading it initialises CUDA). prefer="gpu" turns this off. auto_mode.choose_device, SMALL_QUERY_ROWS.
    2. A cold GPU skips pricing too. While the GPU has not started in this process, a query whose native CPU cost is under the GPU's start-up (240 ms, the lowest measured on the reference box) goes to the CPU unpriced. The CPU cost is bounded high: every operator at the dearest default native rate of its kind (a join with an 8M-row build, a group-by with 1M groups, the radix sort) over all the plan's source rows. Pricing it properly (loading the calibration, sampling keys) would cost about 3 ms of the query's clock. The GPU's start-up is still queued, off the clock, for the queries after this one, unless that finds no GPU. prefer="gpu" turns this off. auto_mode._cold_cpu_bound_ms.
    3. No GPU, a CUDA fault, or a shape that failed before means CPU. A GPU error reruns the query on the CPU with one warning per shape; a CUDA fault switches the GPU off for the rest of the process. strict=True raises instead.
    4. Price both plans. Each operator costs alpha + c·rows on each device, from the calibration. The CPU side is priced as the native executor runs it: a group-by by its group count and a join by its build-side rows, each interpolated between the sizes that were measured. The GPU side is its kernels, plus it pays the copy over the link, the copy back, and whatever is left of its start-up (400 ms by default, until measured). Joins use a measured end-to-end GPU join estimate, padded by 1.15 because it ran low under load.
    5. The GPU must win by a margin. 10% by default, so ties go to the CPU (no memory-capacity risk, no start-up). prefer="cpu" raises it to 30%; prefer="gpu" lowers it to zero. If the GPU would win but is still starting, the query runs on the CPU and says so.
    6. A CPU plan can still use the GPU. For a fused aggregate (filter, expressions and group-by in one pass) with at least 64 MiB of input, the columns are uploaded in the background. Once they are resident, the rows are split statically: the GPU takes the share that makes both devices finish together, from the calibration's pipeline fits and its fixed per-call cost (4.5 ms). A share under 5% either way is not worth it. The resident cache may use 50% of free GPU memory, and an upload that fails or does not fit is retried after 120 s. coproc_fused.py.

    3 · Honest limits

    The 22 and 21 out of 22 were measured before the native Mojo executor

    The three-way runs (cpu, gpu, auto) are from 2026-10-12. The native CPU executor that 0.6.0 ships came after, and auto has not been re-run against it. The 0.6.0 numbers on the front page are device="cpu" only.

    Under device="auto", the native executor runs on a CPU decision

    A CPU decision under auto runs the native executor exactly as device="cpu" does. The co-processing policy, which makes native_exec.try_execute decline, is switched on only when the cost model predicts a CPU+GPU split of a fused aggregate that beats the native CPU executor by 10%, or when you pass gpu_fraction. explain(device="auto", costs=True) prints which path and why. I have not re-measured auto against device="cpu" across the 22 queries.

    check: native_exec.py "CPU+GPU co-processing policy active"

    The CPU+GPU split is still priced against the older kernel

    Since F-058 the whole-query CPU price is the native executor's own: native_global, native_filter, native_group (by group count) and native_join (by build-side rows), measured through compute(device="cpu") on the reference box. Before that, the CPU side was priced from the older kernels, up to 18 times too high on joins, and auto sent five of the 22 SF10 queries to the GPU, where they ran 5 to 9 times slower. The split-versus-native choice still converts the older fused kernel with auto_mode.NATIVE_CPU_FACTOR (1.0), so a split must beat the older kernel by 10%.

    check: auto_mode.py calib.estimate("native_join", "cpu"

    COUNT(DISTINCT) per key always runs on the CPU under auto

    Counting on dictionary codes is a native CPU path (F-046h). Since F-058, auto runs every COUNT(DISTINCT b) per a as device="cpu" does: on the native count where it takes the shape, with the pair as codes wherever the source keeps them (the Parquet reader decides). The GPU is not priced for this shape: its path decodes the columns, and at SF10 it took 6.7 s against 0.66 s. With prefer="gpu" or a GPU placement the columns are decoded and the cost model decides as before.

    check: lazy_frame.py cd_codes = device == "cpu" or codes_decision is not None

    The whole query goes to one device, and there is no per-operator placement

    Placing each operator separately (a CPU filter feeding a GPU join) is ticket F-007 and is not built. placement={"join": "gpu"} sends the whole query to the GPU. The Placer class in auto_mode.py and the ResidencyTracker in residency.py are tested but not on the query path; the cache that matters is in coproc_fused.py.

    Co-processing is one machine, one query shape, and for fused aggregates only

    The split numbers come from a hand-run session on an RTX 3090 on PCIe 4.0 x8 and are in markdown only (docs/auto-mode.md), so they are cited rather than re-run by a script. It needs at least 64 MiB of input already uploaded; a first scan never gets it. Streaming rows to the GPU for a first scan lost on this link; it may pay off on PCIe 5 or unified-memory machines, where the scheduler (coproc.run_router) already exists.

    Parquet is still read through PyArrow

    The three-way runs include the read in the clock (F-021 is the native reader). At SF1 a run takes 50 to 400 ms, so one run varies by about 10% either way, which is why the SF1 verdict is a median of four runs and the single runs are shown too.
