Run conditions

  • Date and build. 2026-10-14, one build (v0.6.0), one machine. Shuffled TPC-H and the three random suites ran 01:21 to 01:50; they started after the load average had stayed under 2 for 5 minutes. The stored-rows TPC-H run was redone at 02:05, after 5 minutes under load 1.
  • The discarded run. The first stored-rows pass overlapped a scheduled snapshot cleanup (snapper); every engine came out slower, so it was thrown away and redone. The only other processes sampled during the rerun were a browser at about a quarter of one core and, in the last sample, one short process at 98% of one core.
  • What the clock covers. The first run of a query in a fresh process: the query and the materialized result. Reading Parquet into memory is staging, outside the clock, for every engine. DuckDB is timed without its pyarrow import for the same reason.
  • A staged warm-up. import omxcore warms its kernel libraries in a background thread that finishes during the untimed load. Polars and DuckDB have no such step.
  • SF1 is noisy. SF1 queries take a few milliseconds, so single figures can move by 10 to 20% between runs. Read SF1 totals more than single queries.
  • Load, as recorded in the files. The load gate (the load average under the limit for 5 minutes) was checked before each run started. The load1 figures below were sampled during the runs, and they include the benchmark's own worker threads: omxcore and DuckDB use every core, so load1 rises while a query runs. A median of 4.7 or 7.3 is not a sign of other work on the machine.

More on the method: optimizations.md. The raw files are in docs/bench.
