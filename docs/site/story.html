omxcore · a data engine written in Mojo

The data engine for the agent era.

omxcore runs SQL on your CPU and your GPU, over the CSV and Parquet files you already have. It's one native library, written in Mojo, with no Python inside. Apps link it like SQLite. Agents talk to it in JSON.

Your files stay yours.

No import, no new format, nothing to convert. Point it at a CSV or a Parquet file and ask. What it writes, every other tool reads.

Your hardware, all of it.

Most laptops and workstations have a GPU that analytics engines never touch. omxcore decides per query whether the CPU or the GPU is faster, and says why.

Answers an agent can trust.

Exact decimals, errors with a line, a column and a hint, and a note for every decision the engine made. Nothing to guess.

The differentiator

Written in Mojo, top to bottom

DuckDB is C++ and runs on the CPU. Polars is Rust and runs on the CPU. GPU engines like cuDF are CUDA, tied to NVIDIA and driven from Python. omxcore is an analytics engine written in Mojo from the SQL parser to the GPU kernels, in a language built for exactly this: CPU and GPU code in one language, compiled ahead of time.

One language, CPU and GPU

The SQL parser, the planner, the SIMD CPU kernels and the GPU kernels are all Mojo. No CUDA C++ beside a Rust core, no Python glue in between. One codebase to make faster.

mojo/omxcore · kernels/

Compiled like C++, reads like Python

Ahead-of-time native code with SIMD types, compile-time specialisation and no garbage collector. Kernels are specialised at compile time, so the hot loop carries no branches it doesn't need.

Mojo 1.1 · AOT · no GC

Not tied to one GPU vendor

Mojo targets NVIDIA, AMD and Apple GPUs from the same source. Today omxcore's GPU path is validated on NVIDIA; the others are the next targets, not a rewrite.

validated on NVIDIA · AMD and Apple next

Links anywhere, no runtime

One native library or one binary. No Python to install, no JVM, no server. It links on Linux and macOS (arm64) today.

libpython guard · Mac link check

Modern algorithms

Morsel-driven parallelism, radix-partitioned hash joins without atomics, parallel radix sort, HyperLogLog-sized hash sets, bounded top-k heaps, SIMD bulk Parquet decode, reproducible float sums.

docs/mojo-engine.md

Honest about the trade-off

Mojo is young. Some wins here are the algorithms, not the language, and the docs say which. The compiler is still maturing: one of our tickets waits on a compiler crash today.

Agent-native

Built for agents first, not adapted for them later

An agent needs four things from a data engine: to start instantly with nothing to install, to read any file it's handed, to get answers it can trust, and to learn from its mistakes in one round. omxcore was designed around those, and the agent toolkit comes next.

Today works now

mx: SQL in, JSON out

One native binary that starts in 12 ms. JSON, JSON lines, CSV or Parquet out. No Python environment to install or break.

mx sql · mx explain · mx schema

Any file, no setup

FROM 'orders.csv' or FROM 'events.parquet' just works. Big Parquet files stream automatically, a row group at a time. mx schema shows the columns, types, row groups and null counts of a file before the agent writes a query.

plug and play · FROM 'file'

Answers it can trust

Money is exact: decimals are scaled integers, not floats. Every result carries notes on how it was computed, and EXPLAIN shows each planner decision with its reason. Results are checked against DuckDB in the tests.

notes · EXPLAIN [ANALYZE] · DuckDB oracle

Errors it can fix in one round

A wrong query returns the line, the column and a hint ("did you mean region?") with a distinct exit code, so the agent corrects itself instead of guessing.

{"error": {message, line, column, hint}}
# an agent asks a question of a file it has never seen
$ mx sql "SELECT region, sum(revenue) AS revenue
         FROM 'orders.csv' GROUP BY region
         ORDER BY revenue DESC LIMIT 2"
{"columns":[{"name":"region","kind":"TEXT","scale":0},
            {"name":"revenue","kind":"DECIMAL","scale":2}],
 "rows":[["West",7447518.00],["East",7387482.00]],
 "row_count":2, "truncated":false, "ms":0.83, "device":"cpu",
 "notes":["columns read: region, revenue (2 of 5)", …]}

# and when it gets something wrong, it learns exactly what
$ mx sql "SELECT regoin FROM 'orders.csv'"
{"error":{"message":"column `regoin` not found in table `orders.csv`",
          "line":1, "column":8, "hint":"did you mean `region`?"}}
A real session on a 200,000-row CSV, notes shortened.
