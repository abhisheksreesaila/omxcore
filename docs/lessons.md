- 2026-09-29 · Mojo `parallelize` called from a `.so` loaded by ctypes segfaults (no async runtime in a host process): call `KGEN_CompilerRT_AsyncRT_GetOrCreateCPUDevice` first, as in `kernels_aot/pipeline_cpu.mojo`.
- 2026-09-29 · The stdlib `Atomic` is sequentially consistent, so NVPTX fences around every atomic (float64 shared-memory accumulation ran ~100x slower than it should): use `llvm.atomicrmw` with monotonic ordering for accumulation (`_atomic_add_f64` in `kernels_aot/pipeline_gpu.mojo`). Separately, float64 compares run at 1/64 rate on GeForce: compare columns in their own type (CMPC), not widened to float64.
- 2026-09-29 · A Bool captured by a `@parameter` GPU kernel closure was read wrong (all rows went to group 0); compute such flags inside the kernel from Int arguments, and write GPU kernels as plain `def`s with explicit arguments.
- 2026-09-29 · The existing GPU sort/gather post-op rounds every float64 column to float32 (sums off by 1 part in 1e8); sort small aggregate results on the CPU.
- 2026-09-30 · GPU 1 is shared with other agents (fixed launch cost jumps 0.1 ms to 6.7 ms when busy): compare kernel variants back to back in one script and quote `_repeat` steady-state numbers, never single runs.
- 2026-09-30 · Comparing float32 data with a decimal literal in float64 drops every row equal to the literal (TPC-H Q6 lost 54% of its revenue on CPU): a float32 column takes the literal as float32, like DuckDB, Polars and NumPy 2.
- 2026-09-30 · A cache keyed by `id(obj)` must hold a reference to `obj` and check identity on lookup; ids are reused after garbage collection, which returned another table's results (found in F-010 review).
- 2026-09-30 · Judge correctness against DuckDB, never against our own CPU path: GPU Q6 (8.865e7) looked wrong next to CPU (4.07e7), but DuckDB gives 8.865e7 — the CPU path dropped boundary rows comparing float32 columns to float64 literals. GPU paths not yet verified against DuckDB go in `auto_mode.KNOWN_BROKEN_GPU`.
- 2026-09-30 · A DuckDB reference over the raw float32 columns shares the data's own errors (the generator truncated 0.05 to 0.049999997, so Q6 "matched" at 8.865e7 while the official answer is 123141078.2283): build the reference through views that restore DATE and DECIMAL(15,2), and check known official answers (Q6 SF1).
- 2026-09-30 · A result cache must be keyed by everything that changes the result, device included: `_JOIN_RESULT_CACHE` without it let `device="gpu"` tests reuse the CPU's join, so the GPU join path (and its SF10 out-of-memory) was never exercised.
- 2026-09-30 · The Mojo device-context memory manager reserves ~90% of free GPU memory when the first kernel-side buffer is created (the recursive scan at >= 1M rows), starving our own cuMemAlloc and every other process on the GPU: `aot_kernels` sets `MODULAR_DEVICE_CONTEXT_MEMORY_MANAGER_SIZE_PERCENT=25` before any GPU use. Observed with a 5% pool: `sort_topk` of 250M rows printed `oom log` on stderr and returned all-zero indices with no exception (kernels swallow errors); the scan was not seen to fail that way, but `hash_join` now raises if its prefix sum is 0 over non-zero counts.
- 2026-09-30 · `pyarrow.Table.join` defaults to a LEFT OUTER join: pass `join_type="inner"`.
- 2026-09-30 · On the query path never call pa.array / pa.scalar / Array.to_numpy / fill_null(<python value>) / compute with Python literals / pq.read_table: PyArrow then imports pandas (~150-200 ms per fresh process). Use np_arrow.array / scalar / to_numpy and ParquetFile; tests/test_np_arrow.py guards it.
- 2026-09-30 · Never chain `git commit` after `pytest ... | tail`: the pipe hides pytest's exit code and a red test got committed. Capture the exit status (`> log; rc=$?`) and commit only when it is 0.
- 2026-09-30 · An operator above an Aggregate (Project, Filter, another Aggregate) or any Aggregate input that is not `Filter*(Scan)` must run on a materialized table (`_materialize_barrier`): the aggregate paths only look at the Scan under them and used to ignore what sat above or between. Add a fuzz seed (tests/test_f016_fuzz.py) when a new plan shape breaks.
- 2026-09-30 · A numeric literal next to an array takes the array's type in arithmetic (`_arith_operands`): a float32 literal array turned `int + 2` into float32 and rounded `float64 + 0.1`.
- 2026-09-30 · A plan shape the fused pipeline declines falls to the `gpu_aot` path, which accumulates float64 in float32 (fuzz seed 5061): when a new plan shape reaches the GPU, check `last_compile_provenance["path"]` is `fused_pipeline_*`, and inline a Project under a grouped Aggregate before `try_fused_aggregate`.
- 2026-09-30 · A scan's column pruning works on names the query uses, but a join renames clashing right columns (`x` -> `x_right`): keep the source column whenever a referenced name is its renamed form (`io_parquet._renamed_ref`).
- 2026-09-30 · `pyarrow.parquet` row-group stats and `ParquetFile.schema_arrow` report dictionary types when `read_dictionary` is set: look through them (`_kind`) before deciding a column is not a string.

- 2026-09-30 · Every caller of AOTKernels.sort_indices (radix sort) must verify the result is a sorted permutation and fall back to np.argsort: one bad order was seen once and never explained, and F-020's group encoder skipped the check (review caught it).
- 2026-10-12 · A shortcut guard (here `n_codes * 16 < n`) can make a test silently exercise the fallback instead of the new path: assert the new path ran (non-None result, provenance), not only that the answer is right.
- 2026-10-12 · A per-query "within X%" check on 50–400 ms first runs is mostly noise in one run (SF1 auto vs cpu: 17–21/22 across 4 runs of the same code): judge it on the median of several fresh-process runs, and report every single-run count, not the best one.
- 2026-10-12 · Don't name the cause of a benchmark loss, or title a ticket by a cause, without a measurement that isolates it; and drop queries whose isolated time is worse than the combined one before splitting a sum (they measure something else). benchmarks.md blamed decode for five queries; the engine-only run showed it held for some, not all.
- 2026-10-12 · PyArrow imports pandas whenever it builds an empty array from Python (`pa.array([])`): zero-chunk `combine_chunks()` / `to_numpy()`, masked NumPy input, an empty `isin` list, and also `Table.group_by` / `Table.join`. Use `np_arrow.combine` / `value_set` / `array`; tests/test_no_pandas_tpch.py runs all 22 queries on tiny data, where empty intermediates actually occur.
- 2026-10-12 · In a native pipeline, don't materialize an n_rows-sized intermediate (a 240 MB group-id array made SF10 Q1 156 ms; encoding keys per 64k-row morsel and aggregating at once made it 66 ms). And time first runs in fresh processes: warm repeats reused freed pages and hid the cost.
- 2026-10-12 · Judge a start-up optimization on import + first query together in a fresh process: preloading the Mojo runtime cut the first query 23 → 5 ms but grew `import` 124 → 143 ms (dlopen serializes on the loader lock), the same total.
- 2026-10-12 · A warm benchmark must clear the engine's own caches before every timed run, not just between queries: the old "hot median of 3" tables let MXFrame reuse its warm-up's join results (Q9 0.6 ms) while Polars and pandas recomputed, and that 20/22 was quoted as a win for months.
- 2026-10-12 · Before scoping an executor milestone, log every plan that reaches the native hook and why it declines (`/tmp`-style coverage run over all 22 queries): M1 looked like "Q1 and Q6" on paper, but joins are materialized first, so the final aggregate of 16/22 queries was in reach, and the decline counts ordered the work.
- 2026-10-12 · When a lazy import moves a fixed cost from `import` into the first query, compare import + first query, not the first-run column alone: the small-data run looked 4x worse (145 → 635 ms) while what a user feels improved (3,503 → 3,245 ms).
- 2026-10-12 · Every place that turns int64 into float64 (the bytecode interpreter) must decline values past 2^53: `x > 2^53` on 2^53+1 returned no rows natively. Test with keys past 2^53 whenever a new path reads int64.
- 2026-10-12 · A benchmark that passes every correctness check can still be timing the fallback: a new module-level helper (`_key_kind`) shadowed an existing one and the executor quietly declined on every query. Grep for a name before adding a module-level function, and check which path ran (`last()`, `last_filter()`, traces) before trusting a speedup or a slowdown.
- 2026-10-13 · Arrow's own methods (`Array.cast`, `Table.filter`, `.take`, `.dictionary_encode`, `.is_null`) import `pyarrow.compute` (~22 ms per process): engine code calls `pc.<fn>(x, ...)` from `_lazy_pc` instead. And a background warm-up that is still running when a short query starts competes with it for the GIL: time it with fast loads (Q1, Q6 at SF1) before moving work there.
- 2026-10-13 · sqlglot keeps LEFT / RIGHT / FULL in a join's `side` and SEMI / ANTI / OUTER / CROSS in `kind`: reading only `kind` turned SQL `LEFT JOIN` into an inner join, silently. Every SQL construct the front end maps gets a DuckDB-checked test per variant, and unknown variants raise instead of defaulting.
- 2026-10-13 · A group key's output name is `e._alias or e.args[0]`, never `args[0]` alone; when touching key naming, check every group-by path (native, fused, kernel, GPU, SQL) and reproduce a ticket before trusting its symptom (F-040 had turned from a KeyError into a silently wrong column name).
- 2026-10-13 · DuckDB imports pyarrow inside its first `.arrow()` call (~70 ms per fresh process): every engine-only DuckDB time had it in the clock, which made the SF1 "beats DuckDB 22/22" mostly an artifact. Any library an engine imports lazily on its first result belongs in staging (import), for every engine; check a first-run outlier against a repeat run before believing a cross-engine gap.
- 2026-10-13 · When a fast path hands its input to another path, check the second path accepts everything the first did: sending sorted few-run input to the hash count made sparse key ranges (which the runs path answered) decline to Python. Test the handoff with an input only the first path could take.
- 2026-10-14 · Benchmark runs for publication: log what else ran (ps samples) and check scheduled jobs (snapper, timers); a load gate at the start doesn't guarantee a quiet run.
- 2026-10-14 · Before opening a PR, run every step in .github/workflows/test.yml locally (the scripts/_test_*.py smoke scripts aren't in pytest).

- 2026-10-16 · In an agent worktree (folder name with hyphens), run tests with `pixi run test` (it runs pytest through an `mxframe`-named symlink); plain `pixi run pytest` can't import the repo package there and every test errors. `pixi run test tests/test_x.py[::name]` runs just that file (fixed in the script after agents kept running the whole suite by accident).
- 2026-10-15 · A sort over a group-by must name the group keys as its last columns on every path (`_key_tiebreak`): relying on a hash table's output order or an unstable top-k partition gave different tie orders per path.
- 2026-10-15 · Check a ticket's claim about DuckDB behaviour by running DuckDB before coding it: F-042 said a duplicate output name raises in DuckDB; `duckdb.sql(q).arrow()` / `.df()` renames the second to `x_1`, while `con.execute(q).to_arrow_table()` keeps both names.
- 2026-10-16 · A count over "any column in scope" is not a row count: COUNT(*) must not read a column that can hold NULLs (F-042 review: HAVING COUNT(*) lost the NULL group). Test aggregates and keys on a fixture whose first column and group keys have NULLs.
- 2026-10-16 · Judge "fully native" with a script that logs what ran (hooks, declines, every PyArrow compute call and its size: `scripts/native_coverage.py`), and size a call by what it processes (a `take` by its indices, not its source): the first hand table counted Q3's small top-k take by its 147k-row source and called it Arrow row work.
- 2026-10-16 · Don't compare a float aggregate with itself across two runs (`total == (SELECT max(total))` where the main plan recomputes the aggregate): the executor's parallel float sums are not bitwise reproducible (measured, SF1 revenue per supplier, 30 runs: ~5.7k of 10k group sums differ from run to run, the global sum took 20 distinct values), so equality can match nothing. Materialize the aggregate once and take the maximum of that table.
- 2026-10-16 · A kernel wrapper with fixed slots (`group_composite`: 4 key slots) must decline when given more, and its test must use slots + 1: a 5-key GROUP BY silently dropped the fifth key (found only because SQL Q18 groups by five columns while the DataFrame Q18 uses two). Write the SQL / second-phrasing of a query before trusting its DataFrame version's coverage.
- 2026-10-16 · A tolerance "tie" is not transitive: a checker that treats near-equal floats as tied and then demands the next sort key flags correctly sorted rows (F-073: seed 7129 matched DuckDB bit for bit and was reported WRONG for months). Before blaming the engine, diff its output against the reference exactly and count strict violations.
- 2026-10-16 · A cache keyed by buffer address never hits for a source that is re-read on every query (`scan_parquet`, a new `read_parquet` call): GPU residency freed each upload when that query's table died, so "repeat queries are resident" was only true for in-memory tables. Probe the repeat case per source kind (file via `scan_parquet`, file via `read_parquet`, in-memory) before building on a cache; key file reads by file identity + columns + pushed filters, and the group ids by a fingerprint of their keys.
- 2026-10-16 · Calibrated `pipeline@gpu` is steady-state compute (~0.1 ms fixed); the 4.5 ms per GPU call (F-006) is not in it: add it when pricing a split or the GPU alone, or small queries look like GPU wins.
- 2026-10-16 · Agent worktrees branch from `origin/main`, and local main is unpushed (180+ commits ahead), so every developer brief must say "first `git merge main` (local main)"; a suite count far below main's (2,6xx vs 3,7xx) means a stale base.
- 2026-10-16 · Mojo's `SIMD.ne` is an ordered compare (`NaN.ne(NaN)` is False, unlike NumPy and C's `!=`): the first NaN-aware kernel built on `x.ne(x)` changed nothing. Test NaN with `~x.eq(x)` (scalars: `not (x == x)`), and run a NaN case against the rebuilt library before building on a compare.
- 2026-10-16 · NaN has many bit patterns (`inf - inf` is a negative NaN, a NaN column value is positive): anything that hashes or ranks floats by bits (dictionary_encode before a sort, `is_in`, group keys) splits them and ties no longer tie; `is_in` also tells -0.0 from 0.0. Canonicalize (`x + 0.0`, NaN -> `np.nan`) before keying by bits, and put both NaN kinds and both zeros in float tests.
- 2026-10-16 · `lf.last_compile_provenance["path"]` names the LAST plan that ran: a projection or filter above an aggregate reports `pyarrow_shortcut` whatever ran the aggregate. Tests that assert an engine ran record the path of every `_compile_and_run` (tests/test_f070_nan_compares.py `cfg`).
- 2026-10-16 · Run a long suite with its output saved to a file (`> log 2>&1`), never through `| tail`: the faulthandler stack dump of a hang is only useful if it is kept, and ptrace (gdb / py-spy) is not allowed on this machine.
- 2026-10-16 · Mojo's `parallelize` / `sync_parallelize` run each task with flush-to-zero + denormals-are-zero set (MXCSR 0x9FE0), so threaded kernels read 5e-324 as 0 while single-thread paths and the GPU did not: launch workers only through `kernels_aot/_fpenv.mojo` (`par`, `par_n`, `sync_par`), and test float kernels with denormals on enough rows that they start threads (tests/test_f082_denormals.py).
- 2026-10-16 · A weakref/__del__ callback runs on any thread, even one inside `with lock:` (the GC fires at any allocation): it must never block on a non-reentrant lock the same code takes (F-107: `coproc_fused._evict` hung the test process on a futex). Queue the work or use a non-blocking acquire.
- 2026-10-16 · A budget check on the size of a merged state is not a bound on the merge: the engine's group-by held ~4x its input (5 MB in, 20 MB peak), so a "state under half the budget" test let the Arrow pool reach 3.4x the budget. Measure the peak of the operation (`pa.default_memory_pool().max_memory()` in a fresh process, after the data is written by another one: the pool's peak is for the process's lifetime) and put the measured factor in the check.
- 2026-10-16 · `ParquetFile.iter_batches` is not incremental by itself: unbuffered, Arrow reads each column chunk whole and decodes the row group before slicing it. Open the file with `buffer_size` (64 KB) to stream page by page; the bound is then the slice plus one page per column.
- 2026-10-16 · Replacing a "declined with a warning" path by a feature: grep the tests for the warning text first (F-056 3b found five tests asserting the old decline) and turn each into a test of the new path, not a deletion.
- 2026-10-16 · `pa.Schema.empty_table()` imports pandas (second slip, after F-026): build empty tables with `np_arrow.empty(schema)`; `tests/test_no_empty_table_method.py` fails on any `.empty_table(` in the package.
- 2026-10-16 · An operation inside a streamed batch has its own working factor: the engine's Sort peaks at 4-5x its input (measured), so sorting a whole batch put the Arrow pool at 5x the budget though the batch itself fitted. Size the pieces an operation sorts from its measured factor (`extsort.SORT_FACTOR`), and profile a bound with the data written by another process: `pa.default_memory_pool().max_memory()` counts what the profiling script itself built.
- 2026-10-16 · Don't merge sorted runs row by row with a comparison written in Python: the engine's Sort is the one definition of the order (NaN, NULLS LAST, DESC, strings). Cut the runs at splitter rows by sorting them together with the splitters (a unique `__seq` as the last key makes the order strict, so a key repeated a million times still splits).
- 2026-10-16 · A result type must follow the input type, never the data: F-037 made an integer SUM a double when a bound proved it fits and int64 otherwise, and F-056 then needed a whole probe (`SumProbe`) so batches and memory agreed on a value-dependent type. Fix the accumulator instead (int64 for integers, F-060) so there is nothing to agree on; when an engine "decides" a type from the values, the next feature has to reproduce the decision.
- 2026-10-17 · Mojo's float `%` (SIMD and scalar) is FLOORED (the sign follows the divisor, Python's), not C's fmod (the sign follows the dividend, DuckDB's): `-7 % 3` gave 2 until the kernels stepped the remainder back by the divisor. Run a negative-operand case against the rebuilt library before trusting any new arithmetic op (F-101).
- 2026-10-17 · Removing a data-dependent route (F-090's pass over the column, which set `exact_sum`) can leave a second consumer of its flag without input: the NULL-aware Arrow path read the same flag and raised "not in range" the moment the pass went away. Grep every reader of a flag before deleting its producer, and keep a test where each consumer is the only path (F-060c).
- 2026-10-16 · (now structure: `scripts/merge_branch.sh` and `tests/test_no_conflict_markers.py`; it happened twice) In a scripted merge, stop if `git merge` fails (`git merge ... && ...`, then check `git diff --name-only --diff-filter=U` is empty) before any `git commit -a`: a later `commit -am` records the merge with conflict markers in the file (happened with docs/plan.md on the F-116 merge).
- 2026-10-17 · "DuckDB's exact double" is a claim to probe, not to assume: `avg` of integers is its HUGEINT total divided in an x87 `long double`, which differs from the correctly rounded quotient for ~1 in 2,000 averages past 2^53 (random small probes agreed with both for 3,000 cases). - 2026-10-19 · A group key's NULL flag comes from `planner.expr_nullable`: an expression op it does not know answered "never NULL", and the NULL group of `GROUP BY CASE ... - 2026-10-19 · DuckDB 1.5.1's optimizer treats `INTERVAL '30' DAY` and `INTERVAL '1' MONTH` as one expression (they compare equal) and answers the wrong column when a SELECT holds both: build oracle columns with `pragma disable_optimizer`, and when an oracle looks wrong, recompute that one expression alone before blaming the engine.
- 2026-10-19 · A text-to-type cast needs three outcomes (reads / certainly not / DuckDB quirk we do not read), fuzzed against TRY_CAST word by word (`tests/test_mojo_cast_fuzz.py`): two outcomes would make a TRY_CAST turn a word DuckDB reads (`1_000`, `0x1F`, `+-1.5`) into NULL, a wrong answer; a quirk is an error, even for TRY_CAST.
- 2026-10-19 · An error flag set by an expression (`OP_FLAG`) fires for every row the block holds, not only the rows a CASE branch takes: gate it with the branch's mask (`_Emitter.guard`) or an untaken `CAST` raises for a row that never reaches it.

- 2026-10-19 · Mojo 1.1 function types (`def(Int) -> None`) are traits: not a struct field, not a default value, not a `[cb: ...]` value parameter that becomes a C function pointer. A callback is a struct that implements a trait (`JobDone`); the generic entry for `pthread_create` is `_entry[Body, Callback]` (F-175).
