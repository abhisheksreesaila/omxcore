# Decisions (Apple GPU, autopilot 2026-10-24)

- D-01 · Apple GPU on by default on macOS, not opt-in · owner's call ("unified memory, GPU comes for free") · reversible: yes
- D-02 · Int64 word on Apple only, chosen at compile time; NVIDIA keeps Float64 · the spec said Int64 everywhere; a global change risks NVIDIA results and speed (done-means 3) for nothing, since Mojo API programs that reach the GPU are integer-only already (`has_float` sends float programs to the CPU) · reversible: yes
- D-03 · No 64-bit atomics on Apple by using modes 0, 3 and 4 (already atomic-free); more groups than mode 4 holds decline to the CPU · the spec's "per-block rows + merge" exists already as mode 4 (F-067); no new kernel · reversible: yes
- D-04 · Fast loop on Linux: `mojo build --emit asm --target-accelerator metal:1` writes each kernel's AIR (`.ll`) without the Mac-only metallib step, so float64, atomics and PTX are caught locally in seconds; the macOS runner is only for running · reversible: yes
- D-05 · The Mac CI has its own pixi manifest (`ci/mac/pixi.toml`, osx-arm64) instead of adding osx-arm64 to the main `pixi.toml` · keeps the main lock file and Linux CI untouched · reversible: yes
- D-06 · Scope: the Mojo package's GPU path only; the Python wheel's AOT GPU kernels stay Linux-only · the app vendors the package; the wheel has no Mac GPU users · reversible: yes
- D-07 · `HAS_GPU` keys on `is_macos() and has_apple_gpu_accelerator()` (first `is_apple_silicon()`, which the runner's virtual M1 is not) · a native Mac build (host CPU apple-m*) gets the GPU; a Linux cross-build that names only the triple (`--target-triple arm64-apple-macosx14.0`, as the app and `check_mac_link.sh` do) reads as not Apple Silicon and keeps its no-GPU object, which it must: Metal kernels need Apple's toolchain at build time · reversible: yes
- D-08 · No `QueryResult.device_name` field: `gpu_device()` plus `r.device == GPU` already say where a query ran · subtract before you add · reversible: yes
- D-09 · Pointers from integer addresses in the kernels use `KAS` (GLOBAL on an Apple GPU, generic elsewhere) rather than passing every buffer as a typed argument · the engine's column table holds addresses; a typed-argument redesign would touch every launch, while the address space keeps one kernel and NVIDIA's PTX unchanged · reversible: yes
- D-10 · M1's premise list now names the device-address-space versions (`int-address`, `address-in-buffer` use `KAS`); the generic-pointer result stays in the report as `generic-int-address` · the premise is "a kernel writes through an integer address", which holds once the pointer is in device memory · reversible: yes
- D-11 · Mode 5 (many groups on the Int64 word: mode 4's ordered walk with the table in device memory, owner thread g % B) rather than 32-bit-atomic emulation of 64-bit sums · deterministic like mode 4, no atomics at all, no device-memory barrier needed (one thread per slot); limit 2^20 (slots + 1) x groups, beyond that the CPU (unified memory) · reversible: yes
- D-12 · Added M6 (Apple's plan on this GPU via `-D OMXCORE_APPLE_GPU_SHAPE`) after review round 1 found no committed test of the Int64 path; two `test_gpu` cases got Apple-aware expectations (44 aggregates now run in 64-thread blocks and must equal the CPU; 3M groups decline to the CPU with a reason) · the suites are the oracle for every case the runner's ten queries miss · reversible: yes
- D-13 · Narrow blocks are 64 threads on Apple (NARROW_B), 128 elsewhere · 32 KB shared memory halves the register file a block can hold; pivots of 20-44 aggregates (the app's) otherwise decline · reversible: yes
